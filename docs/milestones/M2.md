# M2 — Netcode

## Done when

> **2 players in the same playground, authoritative server.**

Two browsers connect to one manually-started server process, each sees their own
Character predicted locally and the other's interpolated, and they can Bump each other —
a Dash into another player knocks them down, exactly like the Spinner or a wall already
do to a single player in M1.

## Scope

Validated at exactly 2 players (matching ADR 0002/0003's original scope), but every data
structure the connection model touches is shaped as a collection of N Characters, not
two hardcoded slots — the real target is up to 12 players, reached in a later milestone
as a config/performance pass, not a rewrite (ADR 0011). No accounts, no lobby, no
matchmaking, no instance orchestration — those stay deferred past M2 exactly as ADR 0002
and the roadmap already said.

Design decisions below came out of a grilling session cross-checked against two
researched briefs: `docs/research/m2-netcode-transport.md` and
`docs/research/m2-client-reconciliation.md`. The resulting architecture decisions are
recorded as ADR 0011, 0012, and 0013 — this checklist is the implementation surface, the
ADRs are the reasoning.

## Checklist

### Server & connection (ADR 0002, 0011)
- [x] A real Node server process replaces the `stepHeadless` stub — a fixed 30 Hz loop
      stepping one authoritative `RapierSimulation` per Match (tickets 01–02; a plain
      `setInterval` loop rather than `advanceFixed`, which is a render-frame helper — a
      drift-correcting server loop is a later refinement)
- [x] WebSocket server (`ws`); each connection gets an anonymous session ID on connect —
      no accounts, no persistence (ticket 02)
- [x] Client sends its `SimInputs` once per sim tick over the socket (ticket 02)
- [x] Server broadcasts a JSON snapshot of every connected Character (and every Prop) to
      all clients once per sim tick (30 Hz) (ticket 02)
- [x] On disconnect, the server removes that Character from the simulation and stops
      broadcasting it; the server process itself keeps running regardless of player count
      (ticket 02; hardened further in ticket 07)
- [x] M2 runs as a single manually-started server process — no on-demand spin-up, no
      orchestration (ticket 02)

### Client prediction & the local world (ADR 0003, 0012)
- [x] Client predicts only its own Character, re-running the shared sim step locally
      (ticket 03)
- [x] Every other connected Character is interpolated between received snapshots for
      rendering (already-built machinery from M1's `interpolateState`, extended to N
      Characters) (ticket 04)
- [x] The client's *local* Rapier world also contains every other Character,
      positioned each tick from the latest snapshot (not simulated, via
      `MirrorCharacter`) — so the local Character's own prediction can't walk through
      them (ticket 04; Props follow in ticket 06)
- [ ] Exception: a Prop the local player is actively pushing is locally simulated for the
      duration of contact, so a push feels immediate; hard-corrected the instant the
      server disagrees (ticket 06)

### Character-to-Character contact — Bump (CONTEXT.md, existing Impact pipeline)
- [x] A Character-to-Character collision computes an Impact magnitude from the two
      Characters' relative velocity (`RapierSimulation.resolveBump`, `BUMP_IMPULSE_SCALE`)
      — reusing `applyImpact`/`IMPACT_STAGGER_MIN`/`IMPACT_RAGDOLL_MIN` exactly as built
      for the Spinner and dash-into-wall in ticket 06 (ticket 04)
  - A fast Dash into another player clears `IMPACT_RAGDOLL_MIN` and knocks them down
  - An ordinary walking bump usually stays under `IMPACT_STAGGER_MIN` — a physical
    shove, no state change
- [x] One-sided: only the Character on the receiving end enters Stagger/Ragdoll; the
      mover is unaffected and keeps their own momentum — a Dash isn't cut short by hitting
      someone (gated on the mover actually driving into the target; ticket 04)
- [x] Resolved authoritatively on the server only — never predicted locally as a state
      change (only the *solidity* is local, via `MirrorCharacter`, per ADR 0012; the
      resulting Stagger/Ragdoll always arrives via a snapshot correction) (ticket 04)

### Reconciliation (ADR 0013)
- [x] Client buffers its own recent inputs by tick number (`InputMessage.tick`,
      `inputBuffer`), plus the position it predicted after each — the server echoes the
      last applied tick in `CharacterSnapshot.lastInputTick` (ticket 05)
- [x] On a server correction to the local Character, replay the buffered
      not-yet-acknowledged inputs forward from the corrected base state
      (`RapierSimulation.replayLocalCharacter`, Bernier-style local replay, not a flat
      snap). The tick-aligned position check (`RECONCILE_POSITION_ERROR`) fires only on
      real misprediction, not the latency gap ticket 03 couldn't tell apart (ticket 05)
- [x] Any correction to discrete `CharacterStateMachine` state (`Controlled → Ragdoll`,
      etc.) snaps immediately — never smoothed (`CharacterController.reconcileTo` +
      `CharacterStateMachine.snapTo`); a Bump-into-Ragdoll snaps and re-anchors to the
      server's pelvis with no replay, since Ragdoll ignores input (ticket 05)
- [ ] Positional error-smoothing for the continuous transform (position/rotation) only —
      optional M2-or-later polish, not a blocker (deferred — replay + hard state snap
      shipped first, per the research brief)

## Explicitly NOT in M2

Accounts · lobby · matchmaking · instance orchestration / on-demand spin-up ·
reconnect support · bandwidth/message-size optimization · Rounds, Qualification, Time
Limit, or any other Match-structure concept (M4) · Grab, Power-ups, Item Boxes,
Spectator Mode, Betting (all "later," post-M4, per the roadmap) · binary snapshot
encoding (JSON is the call for M2 — see ADR 0011).
