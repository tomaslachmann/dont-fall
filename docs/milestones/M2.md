# M2 — Netcode

## Done when

> **2 players in the same playground, authoritative server.**

Two browsers connect to one manually-started server process, each sees their own
Character predicted locally and the other's interpolated, and they can Bump each other —
a Dash into another player knocks them down, exactly like the Spinner or a wall already
do to a single player in M1.

## Scope

Validated at exactly 2 players (matching ADR 0002/0003's original scope), but every data
structure the connection model touches is shaped as a collection of N Characters, not
two hardcoded slots — the real target is up to 12 players, reached in a later milestone
as a config/performance pass, not a rewrite (ADR 0011). No accounts, no lobby, no
matchmaking, no instance orchestration — those stay deferred past M2 exactly as ADR 0002
and the roadmap already said.

Design decisions came out of grilling sessions cross-checked against research briefs in
`docs/research/`. The **canonical spec of the settled protocol is
`docs/networking-model.md`** (living spec — entity model, wire shapes, client time model,
deferred optimizations with triggers); the ADRs (0011–0025) are the immutable reasoning.
The checklist below is the M2-validation implementation surface; the full protocol-v2
implementation surface is `.scratch/m2-netcode/issues/11-protocol-v2-index.md`.

A second grilling session (2026-09) settled the *finished* protocol after ADRs 0015/0016/0017
had accumulated as reactive patches: entity-category model (0018), time sync (0019),
snapshot-rate decoupling (0020), redundant input + LEAD (0021), pushed-Prop prediction
reinstated as a decaying error offset (0022, supersedes 0016), ragdoll replication + a
prediction-tick guard (0023, amends 0015), player identity + reconnect shaping (0024),
Spinner at the prediction tick (0025). Fed by `docs/research/m2-shared-prop-prediction.md`,
`m2-time-sync-and-snapshot-rate.md`, `m2-ragdoll-replication.md`.

Implementing protocol v2 then surfaced one more defect: the *local* Character popped ~one
walk-step backward on a reconcile, ~1×/s while walking. Diagnosed with a deterministic
headless harness (`apps/client/src/predictionRegression.harness.test.ts`), researched
(`docs/research/m2-prediction-reconciliation-loop.md`) → **ADR 0026** (local-player
correction is the same decaying render offset; unconditional sim reconcile; the `0.2`
threshold retired; gentle LEAD drain) and **ADR 0027** (server applies `input[serverTick]`,
not FIFO — closes the systematic bias at the source instead of only hiding it). Tickets 12
and 13 are both **done**.

A subsequent live playtest surfaced three more regressions, all made far more visible by
ADR 0026's much lower reconcile threshold: the camera followed the raw (un-offset) pose, so
every correction the offset hid from the character mesh still popped the camera in full; a
pushed Prop's shove was pinned straight back to the stale server pose on the exact tick
contact first registered (a ticket 06 protection dropped during the ADR 0016→0022 Prop
rewrite); and `DashController` unconditionally ended any in-progress Dash burst on every
reconcile, which under ADR 0026's threshold meant nearly every dash — the "several dashes in
a row, a slight forward jump at the end" report. All three fixed and regression-tested
(`docs/adr/0013` forward note, `docs/adr/0022`/`0026` amendments); see the git history for
the fix commit.

A further live-playtest report (2026-09) — a Bump-into-Ragdoll recipient occasionally left
unable to move, `motionState` still reading `Controlled`, sometimes affecting either or both
players — was investigated but did not reproduce at the shared-`RapierSimulation` level (a
zero-latency two-client harness test passes) and a live 2-browser repro attempt was
inconclusive (headless Chromium doesn't support Pointer Lock; synthetic keyboard input was
unreliable in that environment). Code review of player-identity assignment (per-connection
`randomUUID()`, ADR 0024) and the tab-stall/catch-up path (`predictionAccumulatorMs` capped by
`MAX_STEPS_PER_FRAME`, `predictionTick` reseeded from `estimatedServerTick`) found no
structural cause. Stopped reproducing on retest; left as a known, currently-dormant
intermittent report rather than a confirmed bug — revisit if it recurs with a capturable
artifact (console state, HUD tick/position readout while stuck).

**M2's "Done when" is met**, confirmed by the author's own live 2-browser testing: two
browsers connect to one manually-started server, each predicts their own Character and
interpolates the other, and a Dash-Bump knocks the target down. M2 is done.

## Checklist

### Server & connection (ADR 0002, 0011)
- [x] A real Node server process replaces the `stepHeadless` stub — a fixed 30 Hz loop
      stepping one authoritative `RapierSimulation` per Match (tickets 01–02; a plain
      `setInterval` loop rather than `advanceFixed`, which is a render-frame helper — a
      drift-correcting server loop is a later refinement)
- [x] WebSocket server (`ws`); each connection gets an anonymous session ID on connect —
      no accounts, no persistence (ticket 02)
- [x] Client sends its `SimInputs` once per sim tick over the socket (ticket 02)
- [x] Server broadcasts a JSON snapshot of every connected Character (and every Prop) to
      all clients once per sim tick (30 Hz) (ticket 02)
- [x] On disconnect, the server removes that Character from the simulation and stops
      broadcasting it; the server process itself keeps running regardless of player count
      (ticket 02; hardened further in ticket 07)
- [x] M2 runs as a single manually-started server process — no on-demand spin-up, no
      orchestration (ticket 02)

### Client prediction & the local world (ADR 0003, 0012)
- [x] Client predicts only its own Character, re-running the shared sim step locally
      (ticket 03)
- [x] Every other connected Character is interpolated between received snapshots for
      rendering (already-built machinery from M1's `interpolateState`, extended to N
      Characters) (ticket 04)
- [x] The client's *local* Rapier world also contains every other Character (via
      `MirrorCharacter`, refreshed each frame from the interpolated render position — ticket
      10) and every Prop (pinned each tick to the latest snapshot pose,
      `RapierSimulation.syncPropsToSnapshot` / `Prop.follow`) — so the local Character's own
      prediction can't walk through them (tickets 04 / 06)
- [x] The one Prop the local Character is actively pushing is predicted locally for a
      short grace after last contact, rendered through a decaying render-time error offset
      (ADR 0022, ticket 11.8 — supersedes ADR 0016's "never predicted" below, which read as
      the box popping backward the instant you stopped pushing); every other Prop stays
      interpolation-only, an obstacle in the local world only
      (`apps/client/src/propPrediction.ts`)

### Character-to-Character contact — Bump (CONTEXT.md, existing Impact pipeline)
- [x] A Character-to-Character collision computes an Impact magnitude from the two
      Characters' relative velocity (`RapierSimulation.resolveBump`, `BUMP_IMPULSE_SCALE`)
      — reusing `applyImpact`/`IMPACT_STAGGER_MIN`/`IMPACT_RAGDOLL_MIN` exactly as built
      for the Spinner and dash-into-wall in ticket 06 (ticket 04)
  - A fast Dash into another player clears `IMPACT_RAGDOLL_MIN` and knocks them down
  - An ordinary walking bump usually stays under `IMPACT_STAGGER_MIN` — a physical
    shove, no state change
- [x] One-sided: only the Character on the receiving end enters Stagger/Ragdoll; the
      mover is unaffected and keeps their own momentum — a Dash isn't cut short by hitting
      someone (gated on the mover actually driving into the target; ticket 04)
- [x] Resolved authoritatively on the server only — never predicted locally as a state
      change (only the *solidity* is local, via `MirrorCharacter`, per ADR 0012; the
      resulting Stagger/Ragdoll always arrives via a snapshot correction) (ticket 04)

### Reconciliation (ADR 0013)
- [x] Client buffers its own recent inputs by tick number (`InputMessage.tick`,
      `inputBuffer`), plus the position it predicted after each — the server echoes the
      last applied tick in `CharacterSnapshot.lastInputTick` (ticket 05)
- [x] On a server correction to the local Character, replay the buffered
      not-yet-acknowledged inputs forward from the corrected base state
      (`RapierSimulation.replayLocalCharacter`, Bernier-style local replay, not a flat
      snap). The tick-aligned position check (`RECONCILE_POSITION_ERROR`) fires only on
      real misprediction, not the latency gap ticket 03 couldn't tell apart (ticket 05)
- [x] Any correction to discrete `CharacterStateMachine` state (`Controlled → Ragdoll`,
      etc.) snaps immediately — never smoothed (`CharacterController.reconcileTo` +
      `CharacterStateMachine.snapTo`); a Bump-into-Ragdoll snaps and re-anchors to the
      server's pelvis with no replay, since Ragdoll ignores input (ticket 05)
- [x] Positional error-smoothing for the continuous transform (ADR 0026, ticket 12,
      **done**): the predicted Character's continuous pose is corrected through the same
      decaying render-time error offset ADR 0022 ships for Props (half-life ≈ 100 ms), the
      sim reconciles unconditionally past a float-noise epsilon
      (`RECONCILE_POSITION_EPSILON`), and `RECONCILE_POSITION_ERROR = 0.2` (which equalled
      one walk-step, so a one-tick phase slip popped it) is retired. Discrete `motionState`
      still snaps. The camera follows the same offset-smoothed pose as the drawn mesh —
      a 2026-09 playtest found it still jerking on ordinary corrections when it was fed the
      raw pose instead. Traced from a 2026-09 playtest; research
      `docs/research/m2-prediction-reconciliation-loop.md`
- [x] The server applies `input[serverTick]`, not FIFO next-in-queue (ADR 0027, ticket 13,
      **done**) — closes the systematic ~0.2 u bias ADR 0026's offset could only hide, so
      corrections become rare rather than merely invisible. Validated by
      `apps/server/src/tickAddressedInput.integration.test.ts` against a real, timer-driven
      server (the integration test the headless harness structurally cannot provide).

### Playtest defects — ticket 08 (ADR 0014)
- [x] Dash into a Prop no longer flings the ragdoll clean through it and downrange
      (ragdoll↔Prop collision server-side + `RAGDOLL_IMPACT_VELOCITY_SCALE`)
- [x] Repeated Impacts in quick succession don't leave the Character's mesh tilted
      (`stepWobble` teleport-skip)
- [x] A dash into a wall plays the Ragdoll + GettingUp exactly once, not twice —
      predicted knockdowns are owned by the client's own state machine; a server-reported
      down state is always accepted unconditionally (ADR 0015 — superseded the `bumpSeq`
      gate after 2026-09 playtesting found the client could mispredict its own wall crash
      and then have no way to ever accept the server's Ragdoll)
- [ ] Predicted-ragdoll jitter (`snapRootTo` yanking the pelvis every snapshot) — ticket
      09, stop predicting the local ragdoll body (jitter/cost polish only; no longer a
      correctness dependency for anything)
- [x] Angled dash-into-wall no longer pops on getup — the local Character's down-state pose
      is drawn from the interpolated server snapshot, not local prediction (ticket 10 / ADR
      0015 addendum)
- [x] Running into another player no longer clips through them — mirror capsules are
      refreshed every frame from the interpolated render position (was: once per snapshot
      from the raw pose), and a downed player gets no mirror at all (ticket 10 part 3)
- [x] A pushed box (and every non-predicted entity) moves smoothly — rendered through a
      render-delay snapshot-interpolation buffer instead of a naive last-two-received lerp
      that assumed zero arrival jitter (ADR 0017, `SnapshotInterpolator`)
- [ ] Procedural Wobble lean disabled for M2 (`WOBBLE_ENABLED = false`) — reads as a walking
      micro-stutter once the Character is predicted + reconciled; re-introduce driven from a
      sim-owned velocity, not render-frame position deltas (ticket 08 follow-up)

## Explicitly NOT in M2

Accounts · lobby · matchmaking · instance orchestration / on-demand spin-up ·
reconnect support · bandwidth/message-size optimization · Rounds, Qualification, Time
Limit, or any other Match-structure concept (M4) · Grab, Power-ups, Item Boxes,
Spectator Mode, Betting (all "later," post-M4, per the roadmap) · binary snapshot
encoding (JSON is the call for M2 — see ADR 0011).
