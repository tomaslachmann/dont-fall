# M10 — Visual Module authoring

## Done when

> **A non-artist authors a new visibly-rounded, colored Module in the builder —
> never touching code or Blender — and plays a real Match on it.**

M1–M9 can only place Modules someone else authored: new Module contents are
either typed as numbers (blind) or modeled in Blender (a DCC skill the author
doesn't have and won't learn). The research
(`docs/research/track-module-authoring.md`, revised after the human rejected
blind data authoring) settles the shape: a **compose-from-primitives mode in
the track-builder** (gizmos on boxes/cylinders, rounded + colored preview,
collider wireframe alongside), exporting a registry-ready snippet.

**This milestone is the authoring loop, not a content drop.** M10 makes one
fence and two more Modules to prove the loop; mass-producing Modules is what
the loop is *for*, afterwards.

## Design

Researched first; the full findings are the research note, the decisions
condensed here (no ADR — no shared-architecture change):

- Visuals and colliders stay separate by design: rounded look is
  client/builder-only (`RoundedBoxGeometry`), colliders stay straight Rapier
  cuboids/cylinders built identically on both sides from the same data.
- Look lives on the data as visual-only optional fields, following the
  `surface?` precedent (Module default + per-primitive override, server
  ignores): `cornerRadius?`, `color?`.
- `statics` grows from `FloorBox[]` to a box/cylinder union; a cylinder's
  collider (`ColliderDesc.cylinder`, verified in the installed Rapier) matches
  its visual 1:1, and `axis?` (`x`/`y`/`z`) lays fence rails flat without
  quaternions.
- The compose mode reuses the builder's proven stack (viewport, grid,
  `TransformControls` + new `scale` mode, snapping) — no second editor, no new
  app. In-game build mode was considered and rejected on those grounds.
- Export-and-commit: the builder serializes the draft to a registry snippet
  the author commits. Server-stored Modules stay explicitly out (a content
  pipeline with versioning is a milestone, not a feature).

## Checklist

### Rounded look: radius + color data and render (ticket 01)
- [ ] `cornerRadius?` / `color?` on Module + primitives, resolved with defaults
- [ ] Client + builder render rounded + colored; physics untouched

### Cylinder primitive (ticket 02)
- [ ] `statics` box/cylinder union with `axis?`; Rapier cylinder colliders
- [ ] Client + builder render cylinders; overlap approximated honestly

### Compose mode: gizmos on a Module draft (ticket 03)
- [ ] Translate + scale gizmo editing draft primitives on a grid
- [ ] Dual solid + wireframe render while authoring

### Compose side panel (ticket 04)
- [ ] Primitive picker, radius slider, color picker, cylinder axis
- [ ] Socket/footprint editing without touching code

### Export to registry (ticket 05)
- [ ] Serializer + paste-target docs; exported snippet validates
- [ ] Export → commit → place → playtest loop closed

### First composed Modules + playtest (ticket 06)
- [ ] Fence + two more Modules authored purely in compose mode
- [ ] A real Match played on them (live)

## How this milestone is verified

M7's rule stands: every ticket carries its own live verification in its own
"Done when", and is not done without it. Ticket 06 holds the milestone-level
playtest (a real Match on composed Modules); tickets 01–05 hold render,
physics, and loop proof each.

## Explicitly NOT in M10

Server-stored / downloadable custom Modules (content-pipeline milestone) ·
GLB authoring or converting composed Modules to assets · primitives beyond
box and cylinder (wedges/arcs stay ADR 0055's parametric-block path) ·
enforced color palettes (free hex + palette presets only) · mass Module
production beyond the three proving Modules · anything that changes scoring,
netcode, or Match structure.
