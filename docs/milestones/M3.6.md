# M3.6 — Ground and the movement model

## Done when

> **A Character walks up ramps, slides down the steep ones, and grips ice differently from stone —
> and the old movement still feels exactly like it did.**

Tilted geometry became authorable in M3.5 (ADR 0034) but is not yet something the Character
*relates* to: it walks any slope up to 45° with full control, treats anything steeper as a wall,
and skips down anything steeper than ~18° (~5° mid-Dash) because ground-stick is expressed as a
speed instead of a distance. M3.6 makes the ground a real physical partner, and rebuilds the
movement model it needs to be one.

Design settled over an eight-round grilling session (2026-09) backed by two research passes,
`docs/research/slope-and-surface-movement.md` and `docs/research/surface-and-volume-mechanics.md`.
Recorded as ADR 0035 (persistent-velocity acceleration model), ADR 0036 (Surface/Volume data
model), ADR 0037 (`Sliding`, slope thresholds, speed-gated wall Impact).

**The selection criterion for this milestone:** apart from the `Sliding` state itself, nothing here
adds a replicated field. Every Surface effect is a pure function of position, derived identically on
client and server from the same resolved Track. Everything that needs a latch lives in M3.7.

## Checklist

### The Surface path (delivered end-to-end by the first ticket, with mud as its first user)
- [ ] `RapierSimulation` gains a static-collider handle map, so the Surface under a Character can be
      read from the collider handle the character controller already reports — no new scene query,
      no dependency on collider insertion order (ADR 0036)
- [ ] `Box.surface?` / `Module.surface?`, additive and optional; collapsed `Box ?? Module ??
      "default"` once in `resolveTrack`, never in the tick loop
- [ ] Every previously published Revision (including the M1 seed) parses and resolves unchanged

### Ground contact and slopes
- [ ] Ground-stick becomes a **distance**, not a speed — the unit bug that caps descent at ~18°
- [ ] A spike decides whether Rapier's own snap-to-ground is used: enable it on 0.20.0, measure
      whether the M1-era edge-stalling and Dash-hitching symptoms still reproduce, fall back to the
      project's own distance-based ground-stick if they do (ADR 0037)
- [ ] Two explicit, independent thresholds — walkable → sliding → wall — replacing Rapier's
      coincident 45°/45° defaults
- [ ] New `Sliding` Character state, condition-held while grounded on a too-steep Surface, with
      reduced input; gravity projected along the slope plane applies here and only here
- [ ] An Impact while `Sliding` goes straight to `Ragdoll`

### The movement model
- [ ] Velocity persists between ticks: accelerate toward a desired velocity, then drag, then cap —
      replacing the per-tick `velocity.xz = WALK_SPEED * dir` assignment (ADR 0035)
- [ ] Dash becomes a contributor to that velocity rather than a separate branch
- [ ] Slope speed is an explicit multiplier from the signed slope angle while walking — **not**
      gravity projected onto the plane, which is the rigid-body model and belongs to `Sliding`
- [ ] **Feel is preserved, not re-tuned**: the acceptance criterion is that a player cannot tell the
      difference, guarded by the `predictionRegression` harness

### Surfaces
- [ ] Grip is one per-Surface scalar multiplying **both** acceleration and drag (Source's
      `m_surfaceFriction` model)
- [ ] Ice: near-zero acceleration and near-zero drag, **top speed unchanged** — top speed is not what
      carries the feel of ice in any surveyed engine
- [ ] Mud: capped top speed, acceleration left alone
- [ ] One demo Module per Surface, visually identical to existing pieces — the property is the
      deliverable, the look is not

Mud ships first, in the same ticket that lays the Surface path, because capping top speed works on
the current movement model; ice waits for the acceleration model, because before velocity persists a
grip scalar has nothing to multiply.

### Housekeeping
- [ ] `Checkpoint.volume` renamed to `Checkpoint.trigger`, freeing the word `Volume` for the domain
      term it now has (ADR 0036, CONTEXT.md)

## Explicitly NOT in M3.6

Speed pads, bounce pads, launch pads, updraft Volumes and the speed-gated wall Impact — all of them
need an Epoch latch, and they land together in M3.7 so the protocol changes once · Conveyor belts
(ADR 0036 — disproportionate machinery, nobody asked) · Water and any other liquid · **Any visual
work at all**: new Surfaces look exactly like existing floor, deliberately, while the project is in
dev mode · Re-tuning the feel (ADR 0035 — a separate pass, later, against real ramps and ice) ·
Teaching the random Track generator to produce ramps or Surfaces (still chain-only, zero tilt, as
ADR 0034 left it) · Any Track builder UI for authoring Surfaces · Match structure, Rounds,
Qualification (M4).
