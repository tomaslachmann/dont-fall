# M3 — Procedural Segments

## Done when

> **A Track can be built from Modules — by hand or at random — and a Round runs on it.**

A designer places Modules end-to-end in a standalone Track builder tool and saves the result;
separately, the same underlying store can hold an algorithmically-assembled Track. Either way,
the (ephemeral, per-Match) Match server fetches one fully-resolved Track and runs a Round on it,
exactly as it runs the M1 playground today — just no longer hardcoded.

## Scope

Settled via a `/grilling` session (2026-09), recorded as ADR 0028 / 0029 / 0030 and
`docs/research/m3-track-storage.md`. The roadmap itself is unchanged by this milestone: Grab,
Power-ups, Betting/Spectator and every other "later" mechanic (`CLAUDE.md`) stay exactly where
they were — M3 is only about *building a Track from Modules*, not new Character abilities. A new
domain term, `Projectile` (a runtime-spawned threat, e.g. from a cannon-type Obstacle), was
identified and added to `CONTEXT.md` during the session, but its full design (spawn behavior,
replication) is explicitly deferred past M3.

- **Track topology:** strictly linear (ADR 0030) — no branching for M3.
- **Module footprint:** uniform, fixed-width, straight-run (ADR 0030) — any Module can chain after
  any other with no compatibility metadata.
- **Two Track creation paths, one store:** a hand-built Track (via the builder) and a randomly
  assembled Track are both just rows in the same track-service database (ADR 0028) — the Match
  server never tells them apart, and never generates or holds Module data itself.
- **New persistence layer (a project first):** a separate, always-on Node service
  (`track-service`, likely Docker-deployed) owns a SQLite database (via Drizzle + `better-sqlite3`,
  ADR 0029) for Track documents. This is *not* the future Account/Player system — that stays out
  of scope, tracked separately.
- **Builder tool:** standalone, dev-only (not part of the live multiplayer client), supports
  single-player local playtesting of the Track being built (using the same shared `packages/shared`
  Rapier simulation the real game runs, no networking). It only *places* existing Modules —
  authoring new Module geometry/colliders stays a code-level task, unchanged from today. It must
  show a **visual preview of every Module** in the library (a pickable palette, not just names)
  and a **visual preview of the assembled Track** as a whole (an overview, not only first-person
  placement) — added mid-ticket-breakdown (2026-09) as an explicit requirement, not left implicit.
- **M1's playground is a proof of concept, not a deliverable** — its hand-tuned platforms, Spinner,
  and Props (ADR 0006/0009/0010, M1 ticket 07's feel-tuning pass) get refactored into the first
  engineering-grade Module library, not thrown away.

## Checklist

### Module library (`packages/shared`)
- [ ] Extract M1's hardcoded playground pieces (platforms, Spinner, Props) into reusable Module
      definitions with a uniform footprint (ADR 0030)
- [ ] Module definitions stay usable by both client (render/local test) and server (authoritative
      sim), consistent with the existing `packages/shared` role

### track-service (new)
- [ ] New always-on Node service, SQLite via Drizzle/`better-sqlite3` on a Docker-mounted named
      volume (ADR 0029)
- [ ] Save/load API for hand-built Tracks
- [ ] A "generate a random Track" endpoint that assembles Modules and persists the result as an
      ordinary Track row (ADR 0028) — no separate runtime code path from a hand-built one
- [ ] "Fetch a Track by ID" / "fetch any" — the only two operations the Match server needs

### Track builder (new, standalone)
- [ ] Visual, dev-only tool — place/position/rotate existing Modules into a linear sequence
- [ ] Visual preview/palette of every Module in the library, and an overview preview of the
      whole assembled Track (not just first-person placement)
- [ ] Save to / load from track-service
- [ ] Local single-player playtest (shared sim, no networking, no auth)

### Match server integration
- [ ] Match server fetches a Track from track-service at Round start instead of using hardcoded
      `PLAYGROUND_*` constants — accepting the new runtime dependency this introduces (ADR 0028)

## Explicitly NOT in M3

Branching Tracks · variable Module footprints · Projectile spawn/replication design (deferred,
domain term only) · the Account/Player system · Postgres migration · new Character mechanics
(Grab, Power-ups, Betting/Spectator — unchanged "later" roadmap items) · Round-type-specific
generation rules (Survival/Collect/Team) — Track building stays Round-type-agnostic for M3.
