# M3 — Procedural Segments

## Done when

> **A Track can be built from Modules — by hand or at random — and a Round runs on it.**

A designer places Modules end-to-end in a standalone Track builder tool and saves the result;
separately, the same underlying store can hold an algorithmically-assembled Track. Either way,
the (ephemeral, per-Match) Match server fetches one fully-resolved Track and runs a Round on it,
exactly as it runs the M1 playground today — just no longer hardcoded.

**M3 is done.** All 6 tickets (`.scratch/m3-procedural-segments/issues/`) landed and were
manually verified live (real running processes, and for the builder/playtest, a real browser via
Playwright — not just vitest): the M1 playground now lives as a Module library resolved through
`chainTrack`/`resolveTrack` (01); track-service persists Tracks in SQLite, seeded with the M1
Track (02); the Match server fetches its Track over HTTP at Round start, verified with a raw
WebSocket client against two real, separate processes (03); the Track builder places/saves
Modules with live 3D previews of both every Module and the whole assembled Track, and caught a
real CORS bug no unit test could have (04); a local playtest walks the in-progress Track with the
exact shared simulation, verified by screenshotting a Character crossing a narrow bridge without
falling (05); and track-service can generate a random Track that round-trips through the exact
same store/fetch path as a hand-built one, with the Match server unable to tell the difference by
construction (06).

## Round 2 (2026-09) — the Track builder was a demo, not the deliverable

Landing all 6 tickets proved the architecture end-to-end but left the Track builder itself too
primitive for real content authoring (append-to-end-only, no move/rotate/delete-arbitrary/undo),
the client still ignorant of track-service (only the Match server was switched over — ticket 03's
own scope), and no protection against a malformed Track crashing a Round at start. A second
grilling round, this time explicitly cross-checked against a detailed external architecture
proposal (`docs/track-builder-proposal.md`) and `docs/research/m3-track-builder-v2-architecture.md`,
also settled a real product-scope question that hadn't been asked before: the Track builder is
meant to become a **player-facing feature** (user-created Tracks), not stay an internal-only dev
tool — though real Accounts still don't exist anywhere in the project (ADR 0024), so authorship is
deliberately mocked for now (ADR 0032).

Settled, recorded as ADR 0031 (Sockets/Footprint/Placement rules replace the single global
`MODULE_STEP`; real move/rotate/delete-arbitrary/duplicate/undo via command pattern), ADR 0032
(publish creates an immutable, numbered Revision; mocked `authorId`; a `GET /tracks` list
endpoint since fetch-by-known-id-only isn't a real sharing mechanism with multiple authors), and
ADR 0033 (playability/reachability validation is explicitly deferred to manual Test Mode, not a
`MovementSolver` — that's its own hard problem, same category as M2's time-sync work, not a rider
on this ticket). Plus four smaller, previously-identified correctness gaps: the client also
fetches its Track from track-service instead of the hardcoded M1 import (it was the only remaining
place still doing that); Track saves are validated against the real Module library (a garbage
`moduleId` used to save fine and only blow up when the Match server tried to run it); the Match
server caches the last Track it successfully fetched so a transient track-service blip doesn't
crash an already-running Match; and the Dockerfile/compose setup is actually run once for real,
not just written and assumed correct, and folded into `pnpm dev`.

## Scope

Settled via a `/grilling` session (2026-09), recorded as ADR 0028 / 0029 / 0030 and
`docs/research/m3-track-storage.md`. The roadmap itself is unchanged by this milestone: Grab,
Power-ups, Betting/Spectator and every other "later" mechanic (`CLAUDE.md`) stay exactly where
they were — M3 is only about *building a Track from Modules*, not new Character abilities. A new
domain term, `Projectile` (a runtime-spawned threat, e.g. from a cannon-type Obstacle), was
identified and added to `CONTEXT.md` during the session, but its full design (spawn behavior,
replication) is explicitly deferred past M3.

- **Track topology:** strictly linear (ADR 0030, still holds) — no branching for M3.
- **Module footprint:** originally uniform/fixed-width (ADR 0030); **superseded by ADR 0031**
  (round 2) — each Module now declares its own Sockets + Footprint, placed by aligning Sockets
  rather than chaining a single global step. Still one Socket type for now, so compatibility
  checking stays trivial.
- **Two Track creation paths, one store:** a hand-built Track (via the builder) and a randomly
  assembled Track are both just rows in the same track-service database (ADR 0028) — the Match
  server never tells them apart, and never generates or holds Module data itself.
- **New persistence layer (a project first):** a separate, always-on Node service
  (`track-service`, likely Docker-deployed) owns a SQLite database (via Drizzle + `better-sqlite3`,
  ADR 0029) for Track documents. This is *not* the future Account/Player system — that stays out
  of scope, tracked separately.
- **Builder tool:** standalone, dev-only (not part of the live multiplayer client), supports
  single-player local playtesting of the Track being built (using the same shared `packages/shared`
  Rapier simulation the real game runs, no networking). It only *places* existing Modules —
  authoring new Module geometry/colliders stays a code-level task, unchanged from today. It must
  show a **visual preview of every Module** in the library (a pickable palette, not just names)
  and a **visual preview of the assembled Track** as a whole (an overview, not only first-person
  placement) — added mid-ticket-breakdown (2026-09) as an explicit requirement, not left implicit.
- **M1's playground is a proof of concept, not a deliverable** — its hand-tuned platforms, Spinner,
  and Props (ADR 0006/0009/0010, M1 ticket 07's feel-tuning pass) get refactored into the first
  engineering-grade Module library, not thrown away.

## Checklist

### Module library (`packages/shared`)
- [x] Extract M1's hardcoded playground pieces (platforms, Spinner, Props) into reusable Module
      definitions with a uniform footprint (ADR 0030) — ticket 01, `track/Module.ts`,
      `track/Track.ts`, `track/modules.ts`. Not byte-identical to the original hand-tuned
      geometry (the uniform footprint doesn't allow M1's varying per-stop widths/gaps); same
      beats and tuning values, re-authored to fit the new convention
- [x] Module definitions stay usable by both client (render/local test) and server (authoritative
      sim), consistent with the existing `packages/shared` role

### track-service (new)
- [x] New always-on Node service, SQLite via Drizzle/`better-sqlite3` on a Docker-mounted named
      volume (ADR 0029) — ticket 02
- [x] Save/load API for hand-built Tracks — `POST /tracks`
- [x] A "generate a random Track" endpoint that assembles Modules and persists the result as an
      ordinary Track row (ADR 0028) — no separate runtime code path from a hand-built one —
      ticket 06
- [x] "Fetch a Track by ID" / "fetch any" — `GET /tracks/:id`, `GET /tracks/any`

### Track builder (new, standalone)
- [x] Visual, dev-only tool (`apps/track-builder`) — place existing Modules into a linear
      sequence by clicking a palette entry (auto-chained, ADR 0030) — ticket 04
- [x] Visual preview/palette of every Module in the library, and an orbit overview preview of the
      whole assembled Track (not just first-person placement) — ticket 04
- [x] Save to / load from track-service — ticket 04
- [x] Local single-player playtest (shared sim, no networking, no auth) — ticket 05

### Match server integration
- [x] Match server fetches a Track from track-service at Round start instead of using hardcoded
      `PLAYGROUND_*` constants — accepting the new runtime dependency this introduces (ADR 0028) —
      ticket 03

## Explicitly NOT in M3

Branching Tracks · Projectile spawn/replication design (deferred, domain term only) · the real
Account/Player system (ADR 0024 — `authorId` is deliberately mocked, ADR 0032) · Postgres
migration · new Character mechanics (Grab, Power-ups, Betting/Spectator — unchanged "later"
roadmap items) · Round-type-specific generation rules (Survival/Collect/Team) — Track building
stays Round-type-agnostic for M3 · a `MovementSolver`/reachability-graph playability validator
(ADR 0033 — manual Test Mode only) · the asset/GLB/CDN pipeline (Modules stay code-defined, never
player-uploaded meshes) · share codes, discovery, search, tags, likes, moderation queues (need
real Accounts first; a flat `GET /tracks` list is the only "browse" capability for now).

Superseded from the original scope: **variable Module footprints are now IN scope** (ADR 0031
replaces ADR 0030's single global step with per-Module Sockets/Footprint) — the "uniform footprint
only" line from round 1 no longer holds.
